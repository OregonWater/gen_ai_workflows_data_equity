### Windows render startup — shared sandbox lock

- feeds: docs/workflow-literacy, docs/reproducibility-notes, admin/project-log

Disabling renv's sandbox allowed R to start and all 27 Quarto targets to render. Changing the locale alone did not resolve the stall.

Further inspection of installed renv 1.2.4 and traced startup located the wait in sandbox lock acquisition. The lock's owner was a live R subprocess whose parent was VS Code's R language server. No user process was terminated and no shared lock was removed. Why the subprocess retained the lock was not established. Documentation was checked for the supported sandbox-path setting; the online documentation describes a newer renv version, so installed code and local trials were checked separately.

A new sandbox path allowed startup with sandboxing enabled. The persistent repair sets a per-session temporary sandbox path in .Rprofile on Windows before renv activation. It deliberately replaces inherited sandbox-path settings on Windows so child R sessions also use independent directories. This preserves sandbox isolation while avoiding contention with the shared cache. No dependency upgrade, global configuration change, or change to the project's package versions is required. Temporary sandboxes are recreated by each R session. No delegation was used; the author requested a persistent repair, and the implementation choice is the assistant's.
